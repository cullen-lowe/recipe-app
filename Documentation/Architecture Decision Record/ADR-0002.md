# Context

The Recipe Vault project initially explored multiple architectures including:

- Obsidian-first system of record with local filesystem dependency
- Hybrid sync between Obsidian vault and cloud database
- Cloud-first system with optional Obsidian integration

The goal evolved toward a system that:

- Is accessible from any device (including mobile)
- Does not depend on a local machine or filesystem to function
- Still allows Obsidian to be used as a fast authoring and prototyping tool
- Produces a portfolio-grade full-stack application suitable for deployment

The system must remain lightweight, maintainable, and suitable for incremental development and learning.

---

# Decision

We will adopt a **cloud-first system of record** architecture with an **Obsidian-based authoring and import pipeline**.

## Final Architecture

```text
Obsidian Vault (Authoring / Prototyping)
        ↓
One-way Import Tool (Transformation Layer)
        ↓
PostgreSQL (System of Record)
        ↓
Spring Boot API (Business Logic Layer)
        ↓
React PWA (User Interface)
        ↓
Render Deployment (MVP Hosting)
```

---

# Key Architectural Rules

## 1. Obsidian is NOT part of the runtime system

- Obsidian is used only for:
  - writing recipes
  - prototyping structure
  - offline editing
- The application does NOT read the vault directly in production.

---

## 2. PostgreSQL is the system of record

- All application functionality reads from and writes to the database
- The database is the authoritative source of truth at runtime

---

## 3. Import is one-way (MVP)

- Obsidian → Database only
- No required bidirectional sync in MVP
- Re-import is allowed but treated as a controlled operation

---

## 4. API is the only interface for the frontend

- React PWA communicates only with Spring Boot API
- No direct database or filesystem access from frontend

---

## 5. Deployment is cloud-first for MVP

- Render is the primary deployment platform
- AWS is considered a later optional extension, not part of MVP scope

---

# Consequences

## Positive

- Enables fully independent web application
- Removes dependency on local environment or sync tools
- Simplifies runtime architecture significantly
- Keeps Obsidian as a productive authoring tool
- Provides clear separation of concerns:
  - Authoring
  - Transformation
  - Persistence
  - Presentation

---

## Negative / Tradeoffs

- Requires explicit import pipeline (no automatic sync)
- Obsidian is not real-time reflected in the app
- Adds initial ingestion layer complexity (Phase 1)
- Potential duplication between authoring and production data over time

---

## Mitigations

- Keep import tool simple and one-way for MVP
- Treat ingestion as a repeatable batch process
- Avoid introducing bidirectional sync until explicitly needed
- Maintain Obsidian as a flexible, non-critical staging environment

---

# Rationale

This architecture was chosen to:

- Prioritize a usable, always-available application
- Avoid overengineering sync and filesystem dependencies
- Support incremental development from simple MVP to advanced features
- Provide a strong portfolio-ready full-stack system
- Allow future extensibility into AWS or other cloud providers without redesign

---

# Alternatives Considered

## 1. Obsidian-first runtime system
Rejected due to:
- local dependency
- lack of cloud accessibility
- poor production deployment characteristics

## 2. Fully synchronized bidirectional system
Rejected for MVP due to:
- high complexity
- conflict resolution requirements
- unnecessary early optimization

## 3. Cloud-only without Obsidian integration
Rejected due to:
- loss of preferred authoring workflow
- reduced prototyping speed

---

# Outcome

The system will proceed with a **cloud-first architecture supported by an Obsidian-based import pipeline**, deployed initially on Render with PostgreSQL and a React PWA frontend.

This provides the best balance between:

- simplicity
- usability
- learning value
- and production realism
